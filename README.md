# When the Timestamp Lies: Date-Robust Re-ranking for RAG

Code and run outputs for the paper *"When the Timestamp Lies: Date-Robust Re-ranking for Retrieval-Augmented
Generation under Missing and Corrupted Document Dates"* (Kajal and Gupta).

The study asks what happens to date-based re-ranking when document dates are missing or wrong, on the HoH benchmark,
with two open re-rankers (Qwen3-Reranker-0.6B, BGE-reranker-v2-m3). It compares a date tie-break, a content-only recency
judge, a trust-gated fusion, and an adaptive date-trust weight estimated from the collection.

## Layout

| Path | What it is |
|---|---|
| `src/run_experiments.py` | The whole pipeline in one file (data split, pools, corruptions, re-ranker scoring, judge training, grid search, tables, bootstrap, extras, end-to-end test, judge diagnostics). Configured by environment variables. |
| `src/merge_seeds.py` | Joint bootstrap over queries and judge seeds from the `perq_*.npz` files (CPU only). |
| `notebooks/kaggle_run.ipynb` | One-cell Kaggle notebook that embeds the script and runs the named runs (A, B, C, D, G, H, I). Generated by `tools/make_kaggle_notebook.py`. |
| `tools/measure_web_dates.py` | Optional survey of how often real web date sources contradict each other (no GPU; put a real contact address in the `UA` line first). **Not used for any number in the paper.** |
| `results/logs/` | Console output of the runs behind the paper (see below). |
| `results/runD_3B_judge/` | Files written by run D (3B judge): CSV tables, `perq_j3B_s0.npz`, summary. |
| `results/adaptive_seed0/` | Console output of the adaptive-trust table (seed 0). |

## Data

HoH (`russwest404/HoH-QAs` on the Hugging Face hub, 111,972 usable questions) is downloaded by the script. Articles are split by
a hash of the article title: 60% of the articles build judge training pairs, and 40% are split into development (22,487
questions) and test (22,430 questions). 1,200 development and 1,200 test queries are drawn with fixed seeds
(`SEED = 0` for development pools, `SEED + 1` for test pools). Each pool has the current passage, one or two outdated
versions and six distractors (eight passages, or nine with two outdated versions).
Each run also writes `pools_<tag>.json.gz` with the exact pools (query, article title, per-passage title, kind and date, answers), so
that pools can be compared without re-running. (Runs A to D in the paper were made before this export was added; the pool
construction is unchanged.)

## Running

Kaggle (what the paper used): new notebook, accelerator GPU T4 x2, Internet On, upload `notebooks/kaggle_run.ipynb`, edit the
`WHICH` line, and use **Save Version -> Save & Run All (Commit)**.

| Run | What | Rough time on a T4 |
|---|---|---|
| A | judge seed 0 (1.5B), all analyses and end-to-end test (two generators) | about 4 h |
| B, C | judge seeds 1 and 2, main tables only | about 1.5 to 2 h each (the first run in a session also builds the re-ranker score cache, about 1 h) |
| D | 3B judge, main tables and judge diagnostics | about 3 h |
| G | 4B re-ranker (optional) | 2 to 3 h |
| H, I | adaptive date-trust estimator only, seeds 1 and 2 | about 2 h (H, including cache), 45 min more (I) |

Outside Kaggle: `DRYRUN=1 python src/run_experiments.py` runs everything on fake data on CPU in a few minutes, for testing.
A real run needs a GPU with about 15 GB and Internet (Hugging Face).

Environment variables (defaults in brackets): `JSEED` [0], `JUDGE_MODEL` [Qwen/Qwen2.5-1.5B-Instruct], `GEN_MODEL` [none],
`N_QUERIES` [2400], `HOLD10` [4], `N_DISTR` [6], `PASS_SET` [full], `RERANKERS_SEL` [qwen3-0.6B,bge-v2-m3], `GRID` [full],
`RUN_EXTRAS` [1], `RUN_ADAPT_ONLY` [0], `K_EXTRA` [5], `RUN_DIAG` [1], `RUN_E2E_VARIANTS` [0], `E2E_N` [600], `DRYRUN` [0].

Pooled intervals over seeds: `python src/merge_seeds.py perq_j1.5B_s0.npz perq_j1.5B_s1.npz perq_j1.5B_s2.npz`.

## Known limitations

One dataset (HoH), simulated date errors, 1,200 test queries, the adaptive weight evaluated for one judge training, mixtures evaluated at the
large-sample agreement. See the paper's Limitations section.

## Notes on the adaptive weight

- Pair accumulation: `fuse_g` in `src/run_experiments.py` visits each unordered pair of the top-K set once and adds the amount to one candidate and its negative to the other.
- Empty case: when no confident pair with differing dates exists (batch and year-only dates), the agreement is computed as 0 and the weight is clipped to 0. The paper reports this as n/a.
- At weight 0 the fusion keeps the settings chosen for `gated_ft`, so the result need not equal the separately tuned `content_ft` baseline.
